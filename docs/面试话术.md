## 场景二："这个项目你做了哪些技术难点？"

**话术：**

> "我从几个维度来说：

> **一、安全方面。** 接手后发现静态文件路由没有做任何白名单限制——任何人知道路径就能下载 `.env` 文件（数据库密码、API 密钥）和后端源码。我设计了一套**『白名单放行 + 敏感目录默认拒绝』**的机制，前端资源扩展名白名单 + 路径段黑名单，同时后端源码目录、数据目录、隐藏文件全部禁止 HTTP 访问。这个修完相当于把这个项目的安全基线从 0 拉到了及格线以上。
>
> **二、代码质量。** 我安排了三路并行的代码审查，覆盖 AI 调度模块、扩展工具集、抓包和远程会话。发现了 **20+ 个真实 bug**，其中包括 3 个能让进程直接崩溃的严重缺陷（ESM 下使用 require、SSH stream 缺 error 监听、TFTP 引用越界变量），4 个安全漏洞（FTP 路径穿越、PowerShell 命令注入、DHCP 参数校验缺失、抓包文件越权下载），5 个数据一致性问题。修完以后项目的可靠性提升了一个档次。
>
> **三、架构设计。** 这个项目是单进程的 Express 应用，前端 SPA 直接读盘。我引入了**静态资源缓存层**（内存 LRU + gzip 预压缩 + ETag 304），主文件从 405KB 压到 97KB 传输；**前端离线化**把图标库从 CDN 移到本地；**会话存储**改为原子写入 + 串行队列防止并发覆盖。这些改动没有改整体架构，但把性能和安全提升到了可以上生产环境的水平。
>
> **四、可展示的功能点。** Docker 化部署、Linux 服务器监控面板（前端实时仪表盘 + SVG 历史趋势图 + 阈值告警）、AI 自动排障工作流——这些都是面试官一眼能 get 到价值的。"

## 场景四："为什么用 Node.js 而不是 Python/Go？"

**话术：**

> "选择 Node.js 有几个考量：
>
> 第一，这个项目是**运维桌面工具**定位，大部分诊断需要调用本地系统命令（PowerShell、ping、tracert、netsh 等），Node.js 的 `child_process` 在 Windows 上的兼容性比 Python 更好，而且单进程事件循环对于『发出一条命令→等待结果→返回前端』这种 IO 密集型场景非常契合。
>
> 第二，**全栈统一语言**减少上下文切换。前端 SPA 和后端 API 都用 JavaScript，团队成员不需要在两套语言之间切换。
>
> 第三，**Express 生态成熟**，中间件机制很适合做权限拦截链。我们的实现是：请求进来先过 `authContext` 拿到用户信息，然后每个路由在 `handleApi` 里靠函数式 if-return 链处理——看上去朴素，但可读性极好，新增一个 API 5 分钟搞定。
>
> 如果真要说 Node.js 的短板，CPU 密集型的包解析（PCAP 解析）确实不够快，但我们用 `pktmon` 外部进程 + `execFile` 分离出去了，不会阻塞主线程。"

## 场景五："遇到了什么困难？怎么解决的？"

**话术（选一条或组合说）：**

> **选 1 - 安全漏洞排查：**
> "最难的是静态文件泄露漏洞。接手时我测试了一下 `curl http://localhost:3000/.env`——竟然直接把数据库密码和 API 密钥返回了。这意味着任何人只要能访问这个端口，就能拿到所有凭据。而且这个漏洞在代码里存在很久了。
>
> 我的修复方案不是简单地加个黑名单，因为黑名单总有遗漏。我设计了**白名单机制**：前端资源只有 `.html/.js/.css/.svg/.png` 等少数扩展名可以访问，后端代码目录 `server/`、数据目录 `data/`、隐藏文件全部默认拒绝。需要特殊放行的（门店 Agent 脚本、OUI 数据库）走显式白名单。这样即使以后新增了敏感文件，也不会意外暴露。"
>
> **选 2 - 代码审查发现重大缺陷：**
> "代码审查时发现了一个看起来很奇怪的问题——FTP 上传文件时如果用户执行这个功能，整个进程会崩溃，不报错、不恢复，直接挂了。查下去发现是因为 `.mjs` 文件里用了 `require('fs')`，但 ESM 下 `require` 根本是 undefined。运行时走到那里直接抛 ReferenceError，而且是同步回调里抛的，`try/catch` 都救不了。
>
> 这类问题靠测功能是测不到的，因为那台机器可能从来没人用过 FTP 上传。后来我把所有 `require` 都换成了 ESM `import`，并且在所有动态创建 socket 的地方都加了 `error` 事件监听。"
>
> **选 3 - 数据一致性问题：**
> "AI 会话模块存在并发写入覆盖问题。如果用户快速点两次提交，两个请求同时读同一个会话→各自追加消息→写入文件——后写的会覆盖先写的，消息永远丢失。
>
> 解决方案是**每会话串行写入队列**：同一个 sessionId 的写入排成 Promise 链，一个完了下一个再接上。同时把直接写文件改成写临时文件然后 `rename`，这样读的一方永远不会看到半截 JSON。改动本身不大，但影响的是用户数据，不能丢。"

## 场景六："Docker 部署怎么做的？"

**话术：**

> "Docker 化是**多阶段构建**，在 `node:20-alpine` 基础上先装依赖和构建，然后把运行时产物复制到新镜像，最终镜像约 20MB。`docker-compose.yml` 里编排了两个服务——app 和 MySQL 8.0，MySQL 映射到宿主机 3307 端口避免本机冲突。
>
> 有一个设计细节是**健康检查**：docker-compose 的 healthcheck 每 30 秒调 `/api/health`，确保服务真正可用后才标记为 healthy。MySQL 也是等初始化脚本跑完、root 密码验证通过后才标记健康。
>
> 同时配了一套 Nginx 反向代理配置，做了 WebSocket 升级支持（SSH 长连接需要）、gzip 压缩、静态资源缓存等。虽然 Docker 版已经可以直接用，但这个 nginx.conf 是给生产环境做前置负载均衡用的。"
